# 카페 판매·손익·재고 관리 기술 요구사항 문서

- 작성일: 2026-10-12
- 상태: 추천 기준으로 1차 구현 방향 정리 완료. 프로그램 개발·검사·배포는 아직 수행하지 않았다.
- 근거: [PRD](01_PRD.md)의 제품 범위, [FRD](02_FRD.md)의 기능·계산·오류 대응과 사용자 지시 “TRD 문서는 추천대로 하고 완료해줘”.
- TRD: 정해진 기능을 어떤 구조로 만들고, 기록을 어디에 보관하며, 어떻게 검사하고 실행할지 정리한 기술 요구사항 문서다.

## 1. 목표와 경계

매장 한 곳의 운영자 한 명이 Windows 기기 한 대에서 브라우저로 사용한다. **판매 입력 → 메뉴 수익성 → 일·월 손익 → 재료 잔량·부족 확인**을 연결한다. 판매·비용 입력·수정·삭제, 입고·폐기·실측 기록, 저장·재접속, 수동 백업·복원이 필수다.

기획·화면 설계·개발·검사·배포를 합쳐 240분을 목표로 한다. 기술 구성은 이 범위에 맞춰 작게 정한다. 별도 사용자 계정·클라우드·공유 데이터 서버·POS 연동을 추가하지 않는다. 엑셀 양식과 가져오기, 예상 손익, 권장 발주량, 주·분기·반기·연간 조회는 2차다.

## 2. 선택한 기술과 추천 이유

| 부분 | 선택 | 쉬운 설명과 이유 |
| --- | --- | --- |
| 화면 | HTML·CSS·JavaScript 모듈 | 브라우저가 기본으로 읽는 화면·스타일·동작 언어. 기존 시안의 구조를 참고하고 별도 화면 프레임워크 설정을 줄인다. |
| 프로그램 기록 | IndexedDB | 브라우저 내부의 구조화된 기록 저장소. 판매·재고·비용을 저장하고 재접속 때 불러온다. 작은 설정용 저장소인 localStorage에 전체 운영 기록을 넣지 않는다. |
| 최초 자료 | 제공 JSON 한 번 반영 | 엑셀과 JSON은 같은 자료이므로 JSON만 읽는다. 운영자에게 임의 파일 가져오기 기능을 제공하는 것은 아니다. |
| 계산 | 공통 JavaScript 계산 모듈 | 판매창·메뉴·대시보드·재고가 같은 계산을 사용해 결과 차이를 막는다. 시안의 고정 숫자를 계산 근거로 쓰지 않는다. |
| 백업 | UTF-8 JSON 파일 | 기록과 설정·기준정보를 함께 담아 다시 읽을 수 있다. 엑셀 보고서와 다르며 추가 문서 라이브러리가 필요 없다. |
| 실행 | Node.js의 기본 HTTP 기능으로 정적 파일 제공 | 사용자 기기 안에서 화면 파일을 열어주는 작은 실행 도구다. 운영 기록을 외부 서버로 보내는 구조가 아니다. 별도 서버 프레임워크를 쓰지 않는다. |
| 검사 | 계산·자료 검사와 실제 브라우저 흐름 확인 | 숫자 결과뿐 아니라 저장 실패·재접속·복원도 확인한다. |

IndexedDB는 구조화된 데이터를 거래 단위로 읽고 쓰는 저장소이며 접근 주소별로 분리된다. 이 특성에 근거해 한 기기용 저장 방식을 선택했다. [MDN IndexedDB 설명](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)

Node.js의 기본 HTTP 모듈은 이 문서에서 정적 파일을 제공하는 실행 도구로 한정한다. 실제 런타임 버전과 사용 가능 여부는 개발 시작 시 확인하고 버전을 실행 안내에 기록한다. [Node.js HTTP 공식 문서](https://nodejs.org/api/http.html)

시안의 외부 스타일 CDN·폰트·프로필 이미지는 실행의 필수 조건으로 두지 않는다. 필요한 스타일은 프로젝트에 보관하고 기본 글꼴과 문자 아이콘으로 동작 가능하게 한다. 새로운 사진·로고 제작이나 애니메이션을 추가하지 않는다.

## 3. 사용 환경과 실행 방식

- 목표 브라우저는 Windows의 일반 모드 Edge 또는 Chrome 하나를 정해 검사한다. 같은 브라우저·같은 사용자 프로필·같은 주소로 계속 사용한다.
- 주소는 `http://127.0.0.1:4173`으로 고정한다. 외부 접속을 받는 `0.0.0.0`으로 열지 않는다. 화면 파일을 직접 더블클릭하는 `file://` 방식은 사용하지 않는다.
- 포트가 사용 중이면 이유를 알리고 실행하지 않는다. 임의의 다른 포트로 바꿔 기존 자료가 사라진 것처럼 보이게 하지 않는다.
- 실행 도구는 배포용 화면·동작 파일과 최초 JSON만 제공한다. 원본 엑셀·작업 문서·사용자 폴더의 다른 파일을 노출하지 않고 경로 이동 요청과 디렉터리 목록을 허용하지 않는다.
- 기록은 프로젝트의 `data` 폴더나 원본 엑셀에 저장되는 것이 아니라, 선택한 브라우저 프로필 내부 IndexedDB에 저장된다. 운영체제가 정하는 실제 내부 파일 경로는 고정하지 않는다.
- 백업 파일은 브라우저의 내려받기 기능을 사용하며 저장 위치는 사용자가 지정하거나 브라우저 기본 내려받기 설정을 따른다. 프로그램이 임의의 폴더에 파일을 몰래 쓰지 않는다.
- 브라우저 데이터 삭제·프로필 변경·주소 변경 후에는 기존 기록을 볼 수 없을 수 있다. 수동 백업을 다른 안전한 위치에 보관하고 복원하는 사용 안내를 제공한다. 여러 기기 동기화는 없다.
- 브라우저의 저장소 지속 보관 요청은 가능할 때 사용하되 거절되어도 실행은 가능하다. 허용되어도 사용자의 자료 삭제를 막는 기능이나 백업 대체 수단은 아니다. [MDN 지속 보관 요청](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist)

## 4. 내부 구조와 기능 연결

실제 파일을 이번에 만드는 것은 아니며, 다음은 구현 책임을 나누는 기준이다.

| 구성 | 책임 | FRD 연결 |
| --- | --- | --- |
| 화면·목록·입력 | 6개 메뉴 이동, 일·월 선택, 입력·미리보기·오류 표시 | F02~F13 |
| 입력 검사 | 날짜·단위·수량·금액·참조·중복 검사 | F01, F03~F07, F10, F15 |
| 업무 계산 | C01~C10, 마감·잠정 구분, 실측 기준 재고 | F04, F08~F13 |
| 저장 | 최초 반영, 확정 기록 읽기·쓰기, 자료판 번호 관리 | F01, F14 |
| 백업·복원 | 파일 생성·검사·전체 대체 | F15 |
| 실행 도구 | 같은 주소에서 프로젝트 화면·최초 JSON 제공 | 1차 사용 환경 |

화면은 계산 결과를 표시하고 계산 모듈은 기록을 바꾸지 않는다. 저장 모듈만 확정 기록을 바꾼다. 미리보기에서 재고 기록을 추가하지 않는다.

IndexedDB에는 `appState` 저장 묶음을 두고 고정 키 `main`에 전체 업무 자료 한 묶음을 보관한다. 첫 버전은 자료 전체를 읽어 기억 공간에서 조회·계산한다. 거래 한 번에 새 자료 묶음을 교체하는 방식으로 구현 복잡도를 줄인다. 현재 샘플 수준에서 응답 성능을 검사하고, 성능 문제가 확인되면 날짜별 저장 묶음으로 나누는 후속 개선을 검토한다.

각 자료 묶음에는 구조 버전, 자료판 번호 `revision`, 출처, 최초 반영 여부와 원기록이 포함된다. `revision`은 저장할 때마다 하나 증가하며 화면이 오래된 자료로 저장하려고 하면 다시 불러오도록 안내한다. 두 탭의 동시 편집을 협업 기능으로 지원하지 않고 저장 충돌을 막는다.

## 5. 보관할 자료와 연결 규칙

| 자료 | 필수 키·내용 | 제약 |
| --- | --- | --- |
| 매장·출처 | 매장 식별, 원자료 dataset_id, version, 기록 기간, 통화, 부가세 제외 기준 | 가상 샘플임을 유지. 오늘 날짜로 원자료 마감일을 덮지 않음 |
| 공급사·재료·메뉴 | 기존 ID, 이름, 단위, 구매용량, 메뉴 가격·분류·레시피버전 | 기존 대상만 사용. 없는 MAT 코드·카푸치노 등을 추가하지 않음 |
| 레시피·가격이력 | 메뉴·버전·재료·개당 수량·단위·채널, 재료별 적용시작일·구매가격·용량 | 유효 날짜와 같은 단위로 연결. 원가 근거 누락은 계산 실패 |
| 판매 | 기존 필드와 sale_id, 날짜·메뉴·채널·수량·단가·할인·순매출·수수료·당시 개당 원가 | ID 고유, 날짜·메뉴·채널 조합 고유. 수정은 ID 유지 |
| 비용 | expense_id, 귀속일, 기존 항목·금액·배분 설명 | ID 고유. 같은 날짜·항목 여러 행은 허용 |
| 초기재고·재고변동 | 기존 필드, event_id, 날짜·재료·유형·증감량·단위·실측·사유 | 실측과 조정량 구분. 기존 선택적 원가·공급사 보존 |
| 영업달력 | 날짜별 영업·완료·날씨·메모 | 날짜 고유. 새 날짜의 날씨·메모는 미입력 |
| 월비용계획 | 월·기존 비용항목·금액 | 1차 읽기·보존만. 손익 비용에 다시 합산하지 않음 |
| 최소 수량 | 재료ID별 수량 또는 미설정 | 초기값은 미설정. g/ml/개 단위는 재료에서 결정 |

새 판매·비용·재고 ID는 종류 접두어와 충돌 없는 식별자로 발급하고, 제공 ID는 그대로 보존한다. 판매 삭제는 판매 원기록만 제거한다. 연동 결과는 다시 계산하며 실제 재고 입고 행을 만드는 방식으로 판매 삭제를 처리하지 않는다.

원본 파일은 읽기 전용이다. 제공 JSON의 선택적 필드는 백업에도 보존한다. 신규 기록에 없는 값은 빈칸과 0을 구분하고, 형식을 맞추기 위해 가짜 원가·공급사·날씨를 넣지 않는다.

## 6. 날짜와 숫자 처리

- 업무 날짜는 `YYYY-MM-DD`, 월은 `YYYY-MM` 문자열로 다룬다. 한국 날짜의 날짜 자체를 UTC로 바꿔 하루 이동시키지 않는다. 달력에 존재하는 날짜인지 검사한다.
- 신규 판매·비용·재고 날짜는 초기재고 기준일 이상, 사용 기기의 한국 기준 오늘 이하로 제한한다. 최초 조회는 자료의 마지막 완료일이다.
- 일 조회는 그 날짜, 월 조회는 해당 월의 기록을 필터한다. 미완료 판매·비용은 목록에서 잠정으로 구분하고 완료 실적 합계와 섞지 않는다. 완료된 비용은 휴무일이어도 귀속 기간에 포함한다.
- 재고는 판매 사용량을 포함한 모든 기록된 실제 변동을 기준일까지 반영한다. 실적의 마감 필터 때문에 실제 판매 사용량이 잔량에서 빠지지 않게 한다. 월 재고 기준일은 해당 월의 마지막 완료일이며 완료일이 없으면 완료 기준 잔량 없음과 잠정 기록을 구분한다.
- 숫자 입력은 부호·자리수를 검사하고 `NaN`·무한대·숫자 아닌 문자열을 받지 않는다. 쉼표로 구분한 `4,000`은 정상 수량으로 해석하며 단위 문자를 숫자로 읽지 않는다.
- 판매수량·‘개’는 정수, g/ml는 소수 3자리까지. 단가·할인·수수료·비용 입력은 정수 원이다. FRD Q04의 무료 판매·0 비용·실측 0 허용을 따른다.
- 새 개당 원가는 재료 비용 합계를 소수 4자리 원으로 고정한다. 기존 기록의 소수 정밀도는 보존한다. 합계 계산 뒤 원 단위, 비율 소수 한 자리로 표시하며 반올림은 절반에서 절댓값이 커지는 방향이다.
- 금액·수량의 정확한 덧셈·곱셈은 소수 문자열을 정수와 자릿수로 분해해 계산한다. JavaScript `BigInt`를 내부 계산에 사용하고 나눗셈·반올림은 공통 함수 한 곳에 둔다. 예: 1,040.1250원은 10,401,250과 소수 4자리로 표현한다. 직접 `BigInt`를 JSON에 넣지 않고 일반 숫자 또는 십진 문자열로 변환한다.
- 원가·수수료 누락은 0으로 채우지 않고 해당 결과의 계산 불가 이유를 표시한다. 판매 관련 비용·운영비·손익은 FRD 계산식을 공통으로 사용한다.

## 7. 저장과 관련 결과의 일관성

등록·수정·삭제는 입력 검사 → 최신 자료 확인 → 변경 자료 구성 → 저장 거래 완료 → 자료를 다시 읽어 관련 결과 갱신 → 완료 표시 순서로 처리한다.

1. 전체 업무 상태를 읽어 보관한다. 최초 사용이면 제공 JSON을 검사해 한 번 반영하며 반복 반영하지 않는다.
2. 변경할 기록과 관련 날짜의 완료 상태를 새 묶음에 적용한다. 기존 확정 묶음은 저장 전까지 교체하지 않는다.
3. 하나의 읽기·쓰기 거래 안에서 현재 revision을 확인하고 새 묶음을 쓴다. 준비한 자료는 거래를 열기 전에 계산하며 거래 안에서 파일 읽기나 다른 비동기 작업을 기다리지 않는다.
4. 요청 한 건의 성공 이벤트만으로 완료라고 하지 않고 거래 완료 이벤트를 확인한다. 오류·중단 시 기존 묶음을 유지하고 입력창을 남긴다.
5. 완료 후 새 상태로 메뉴·손익·재고를 다시 계산한다. 읽기·계산이 실패하면 “기록 저장됨, 결과 갱신 실패”를 알려 기록 재등록을 유도하지 않는다.
6. 기록의 원가 사본·실측값은 보관하되 대시보드 합계·잔량은 원기록에서 계산한다. 별도 누적 차감값을 저장해 재시도 때 두 번 차감하는 방식은 사용하지 않는다.

IndexedDB 거래에는 완료·오류·중단 상태가 있으며 거래 완료가 운영체제의 모든 장애에 대한 영구 보존을 보장하는 것은 아니다. 이 때문에 재접속 검사와 수동 백업을 함께 요구한다. [MDN IDBTransaction](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction)

## 8. 실측 재고와 과거 수정

재료별 초기재고에서 날짜 순으로 입고·판매 사용·폐기를 반영하고, 해당 날짜의 마지막 단계에서 실측을 적용한다. 실측이 있으면 그 수량을 이후 계산의 출발점으로 삼는다. 같은 날짜·재료의 신규 실측은 한 번만 등록한다.

실측 이전 판매를 수정해도 실제 센 수량은 바꾸지 않는다. 원기록의 실사조정량을 보존하고 현재 기록으로 다시 계산한 설명상 차이를 구분한다. 화면의 누적 변동표는 재계산한 조정 차이를 써서 기준일 잔량과 맞추며, 원본 조정량을 새 차이로 덮어쓰지 않는다. 실측값이 없는 조정 기록은 증감으로 한 번 적용한다.

음수 재고는 기록 오류 가능성을 경고하고 원값을 보여준다. 최소 수량이 미설정이면 판정 보류, 잔량을 계산할 수 없으면 판정 불가다. 부족량은 최소 수량까지의 차이이며 권장 발주량으로 부르지 않는다.

## 9. 수동 백업과 전체 복원

### 9.1 백업 구조

백업은 `prep-cafe-backup_YYYYMMDD_HHmmss.json`으로 내려받는다. 이름의 시각은 한국 기준이며 파일 안에는 UTC 작성 시각도 함께 보관한다.

| 항목 | 내용 |
| --- | --- |
| format | `prep-cafe-backup` 고정 구분 |
| schemaVersion | 백업 구조 버전 1 |
| calculationVersion | FRD의 계산 기준 버전 1 |
| exportedAt | 파일 작성 시각 |
| storeIdentity·sourceMeta | 매장·자료 출처·기간 정보 |
| revision·counts | 자료판 번호와 기록별 건수 |
| data | 기준정보, 판매·비용, 초기재고·변동, 영업달력, 월계획, 최소 수량 |

마지막 저장 완료 상태의 내용을 읽는다. 미저장 입력은 포함하지 않는다. 결과 숫자만 내보내지 않는다. 브라우저에 파일 내려받기를 요청했으면 “백업 파일 내려받기 시작”을 표시하며 실제 디스크 보관을 확인하지 못했는데 완료를 보장하지 않는다.

### 9.2 복원 절차

파일 선택 → JSON 읽기 → 형식·버전·필수 필드·날짜·고유ID·참조·단위·최소 기준·건수 검사 → 포함 기간과 기록 수, 전체 대체 영향 표시 → 사용자 확인 → 하나의 거래로 전체 대체 → 다시 읽어 결과 재계산.

현재 자료와 합치지 않는다. 기존 자료가 남아 있는 동안 파일을 먼저 검사한다. 실패·취소·버전 불일치·다른 매장 자료·중복 판매 조합이면 기존 자료를 변경하지 않는다. 일부만 복원하는 모드를 추가하지 않는다. 최소 기준 미설정도 정상 상태로 복원한다.

파일 내용을 스크립트로 실행하지 않고 데이터로 읽는다. 이름·사유·메모는 화면에 문자로 표시해 파일 안의 HTML이 실행되지 않게 한다. 시안에 있던 관리자 계정·클라우드 인증 기능은 추가하지 않는다.

## 10. 오류와 실행 중 예외

| 상황 | 기술 처리 | 사용자 결과 |
| --- | --- | --- |
| 원자료 검사 실패 | 반영 거래를 시작하지 않음 | 자료 위치와 이유 안내, 재시도 가능 |
| 오래된 화면에서 저장 | revision 차이로 거래 중단 | 최신 기록을 불러오도록 안내, 변경 입력 유지 |
| 공간 부족·권한·저장 오류 | 거래 중단, 이전 상태 유지 | 저장 실패 안내, 성공 문구 없음 |
| 저장 완료 뒤 화면 계산 실패 | 중복 저장 없이 재읽기·재계산 | 저장 여부와 화면 실패를 분리해 안내 |
| DB 읽기 실패·손상 | 자동 초기화·샘플 덮어쓰기 금지 | 기존 자료 접근 오류와 백업 복원 안내 |
| 탭 여러 개·구조 변경 | 구조 변경 시 연결 종료 안내, revision 확인 | 다른 탭 종료 또는 재접속 안내 |
| 수수료·가격·레시피 누락 | 해당 입력·계산 중단 | 누락 항목과 계산 불가 표시 |
| 재고 음수 | 수량 유지, 경고 후 저장 | 재고 기록을 확인하도록 안내 |
| 복원 파일 오류 | 전체 대체 중단 | 필드·기록ID와 이유 표시, 기존 자료 유지 |
| 실행 주소 사용 불가 | 같은 포트 실행 중단 | 주소 충돌 안내, 다른 주소 자동 실행 없음 |

원기록 변경이 없는 조회·검색·페이지 이동은 자료 저장을 요구하지 않는다. 백업 만들기 실패와 프로그램 기록 저장 실패도 서로 구분한다.

## 11. 검사와 배포 완료 기준

검사는 FRD V01~V15를 기본으로 한다. 아래는 앞으로 수행할 검사이며 이번 문서 작업에서 통과한 것으로 표시하지 않는다.

- 초기 JSON의 업무 기록 수와 ID·연결·단위를 확인하고 재접속 때 재반영되지 않는지 검사한다.
- 매장 라떼 10개 예시에서 순매출 48,000원, 식재료비 10,400원, 직접 수수료 720원, 공헌이익 36,880원과 원두 200g·우유 2,000ml 사용을 확인한다. 이 수수료는 설명값이다.
- 판매 채널·날짜 변경, 삭제, 재마감이 이전·새 기간 및 재고에 일관되게 반영되는지 확인한다.
- 단가 0·전액 할인·매출 0·실측 0·기준 미설정·음수 재고·가격 누락을 각각 검사한다.
- 실사 4,200ml→4,000ml의 차이는 −200ml이고 최종 실측은 4,000ml임을 확인한다. 실측 이전 판매 수정이 실측 이후 잔량을 잘못 바꾸지 않는지 확인한다.
- 백업 전·복원 후 원기록·기준정보·계산 결과가 같고, 손상 파일·취소·저장 중단 때 현재 자료가 보호되는지 확인한다.
- 재접속·브라우저 재시작, 두 탭 저장 충돌, 반복 클릭과 재시도에서 중복 효과가 없는지 확인한다.
- 현재 샘플 전체에서 첫 표시 3초 이내, 일반 조회·미리보기 1초 이내를 목표로 측정한다. 저장·복원은 진행 상태를 표시하며 실패를 시간 경과만으로 성공 처리하지 않는다. 목표 충족은 실제 대상 기기에서 판정한다.

배포 결과물은 화면·계산·저장 모듈, 제공 초기 JSON, 고정 주소 실행 도구, 실행·백업·복원 안내다. 시작 파일은 숨김 실행을 사용하며 별도 눈에 띄는 명령창을 필수로 띄우지 않는다. 설치 권한·실행 도구 사용 가능 여부는 구현 시작 시 확인한다.

PRD의 예산은 기획 25분, 화면 설계 20분, 개발 130분, 검사 35분, 배포 15분, 여유 15분으로 유지한다. 실제 개발 시간과 환경에 따라 달라지는 목표다. 핵심 흐름·저장·복원 검사 실패를 기능 삭제나 성공 문구로 대신하지 않는다.

## 12. 완료 상태와 남은 운영 사항

PRD·FRD·TRD의 1차 범위, 권고 동작·계산, 구현 구조와 검사·배포 기준 정리를 완료했다. 실제 재료별 최소 수량은 운영자가 프로그램에서 입력하며 기본값을 지어내지 않는다. 사용할 브라우저 프로필, 실행 가능한 런타임과 백업 보관 위치는 구현·사용 준비 때 확인한다. 이는 새 기능 선택을 기다리는 상태가 아니다.

2차 기능의 전망 방법·기간·엑셀 가져오기 구조는 확장 시 정한다. 이 문서는 코드 작성이나 외부 공개 배포를 수행하거나 완료했다고 주장하지 않는다.
